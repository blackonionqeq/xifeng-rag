# 新文章分块与整体概括联合生成设计

状态：已确认，2026-09-01。

## 1. 背景与目标

当前文章整体概括只读取分块提案或批准清单中的话题标题、块级概括和关键词，不读取规范正文。
这会形成“分块概括再概括”的二次压缩，容易遗漏用户实际记得、但未进入块级概括的次要论述；
没有分块提案的文章也无法生成整体概括。

本改动只调整今后尚未批准分块的文章版本：本地或经用户逐次确认的外部分块模型已经读取完整
规范正文时，在同一次请求中同时生成话题分块元数据和文章整体概括。两者在同一个分块审核页
编辑，并由同一次明确确认共同批准。

既有 `ArticleOverview` 不回填、不重新生成、不自动替换。已经存在批准分块清单的文章版本继续
保持当前行为。

## 2. 已确认方案

采用单次联合生成，而不是分块完成后再次调用全文模型，也不再把块级概括作为整体概括的唯一
输入：

```text
清洗后的规范正文与编号原子单元
  -> 一次结构化模型调用
  -> article_summary + topics[]
  -> 同页人工编辑
  -> 同次确认批准分块清单与文章整体概括
  -> 分别更新证据块索引与文章反查索引
```

联合生成不代表模型可以先生成块级概括、再根据块级概括机械拼接整体概括。Prompt 必须明确要求
模型基于本次收到的完整原文独立归纳 `article_summary`；话题边界、标题、块级概括和关键词与其
并列输出。

## 3. 适用范围与兼容性

联合生成仅适用于尚无 `ApprovedManifest` 的文章版本，包括：

- 首次本地分块；
- 尚未批准分块时对同一版本生成的本地或外部并列重试提案。

下列内容不在本次范围内：

- 给已有批准分块或已有概括的文章批量回填、重写概括；
- 修改已批准且不可变的分块清单；
- 把全文直接写入文章级检索文档；
- 改变现有证据检索、引用或 Generator 的输入边界；
- 为文章搜索引入意图路由或与证据块分数融合。

旧提案和旧审核 JSON 必须继续可读取。新 Schema 与 Prompt 使用新版本标识，不能改变历史提案
身份或复现结果。对已有批准分块清单的文章执行现有维护流程时，不自动创建或替换概括。

## 4. 结构化输出与持久化

新的模型输出顶层结构为：

```json
{
  "article_summary": "80 至 140 字为宜，最多 200 字",
  "topics": [
    {
      "end_unit": 12,
      "title": "话题标题",
      "summary": "块级概括",
      "keywords": ["关键词"]
    }
  ]
}
```

`article_summary` 必填、去除首尾空白、不得为空且最多 200 字。它应先说明文章核心判断，再覆盖
主要论证路径和对文章反查有帮助的重要延伸主题；不得补充外部事实，不得伪装成作者原话。
`topics` 继续使用现有边界、覆盖、顺序、数量和目录残留校验。

分块提案成功后：

1. `ChunkProposalRow` 按现有方式保存结构化话题提案和生成元数据；
2. 同时创建一个绑定该 `proposal_id` 的 `ArticleOverviewRow`，状态为 `pending_review`；
3. 每个并列重试提案拥有自己的整体概括草稿，不能跨提案复用；
4. 提案被废弃或被另一提案取代时，其未批准概括不得进入文章索引；
5. 不保存渲染后的完整模型请求或外部原始响应。

现有 `article_overviews` 已支持 `proposal_id`，预计不新增数据库列。实现时若发现无法在不破坏
历史数据的前提下表达联合草稿，才增加向后兼容迁移，不能把正文复制进新表。

## 5. Prompt 与隐私边界

默认本地 Ollama 分块本来就读取完整清洗正文。联合输出只扩展同一次响应，不新增网络请求，
也不改变本地处理边界。

单篇外部分块重试仍必须显示文章版本、清洗后字符数、服务、模型和最大请求次数，并逐次二次
确认。用户确认后，同一个全文请求可以同时返回分块和整体概括，不需要增加第二次全文外发。
自定义分块 Prompt 只能改变当前重试的分块指导；系统仍须追加不可绕过的结构化输出与整体概括
约束，避免自定义 Prompt 因未提及 `article_summary` 而产生必然失败。

现有 `overviews revise-pending --provider deepseek` 继续只发送派生元数据，不发送正文。它不处理
本次已经与分块一起批准的概括，也不改变“已批准概括不可批量改写”的规则。

## 6. 联合审核与批准

分块审核页在话题编辑区之前展示“文章整体概括”编辑框，并显示它是 AI 草稿、不是作者原话。
保存草案时同时校验并保存：

- `article_summary`；
- 全部话题边界、标题、块级概括、关键词和 `include_in_index`。

页面不提供“只批准分块”或“只批准概括”的分叉。用户点击现有的“批准并更新索引”并二次确认
后，后端在同一数据库事务中：

1. 创建不可变 `ApprovedManifest` 与对应 `TopicChunk`；
2. 将用户编辑后的整体概括批准为该文章版本的活动 `ArticleOverview`；
3. 将同版本、同用途的其他未批准概括按现有替换规则处理，避免多个草稿同时进入候选选择。

随后分别构建并发布：

- 证据块索引；
- 文章级反查索引。

两个索引 Build 都采用现有“构建完成后再切换”的发布方式。任一构建失败时，对应旧活动 Build
继续服务；数据库中的批准记录不回滚为待审，审核页显示哪一个 Build 失败并允许幂等重试。只有
两个 Build 均成功后，审核会话才显示完成并允许关闭。不得出现半成品目录成为活动索引的情况。

## 7. 失败处理

- 模型缺少或生成超长 `article_summary`：视为结构化生成失败，与其他 Schema 错误一起进入现有
  有限重试；错误诊断不得包含正文或完整响应。
- 话题覆盖不完整：整体概括即使有效，整份联合提案仍失败，不能单独保存概括。
- 草案概括为空或超过 200 字：拒绝保存并在页面给出明确字段错误。
- 概括批准失败：分块与概括的数据库批准事务整体失败，不构建任何新索引。
- 证据索引或文章索引构建失败：保留各自旧活动 Build，展示可重试状态，不重复创建新的批准
  清单或概括。

## 8. 验证要求

至少增加以下自动化验证：

1. 新联合 JSON Schema 使用 Ollama 可接受的保守子集，并要求 `article_summary` 与 `topics`；
2. Pydantic 校验概括非空、长度上限以及既有话题覆盖规则；
3. 默认 Prompt 和自定义 Prompt 路径都要求模型从完整原文独立生成整体概括；
4. 首次分块与未批准重试分别产生绑定正确 `proposal_id` 的待审概括；
5. 旧提案、旧审核 JSON 和已有批准文章仍可按原行为读取，不触发回填；
6. 审核页可以加载、编辑、保存整体概括和话题草案；
7. 单次确认原子批准分块清单与概括，重复提交保持幂等；
8. 证据块索引和文章索引均更新，新文章可立即被两类查询发现；
9. 分别模拟两个索引的构建失败，确认旧 Build 保持活动且页面可重试；
10. 默认本地路径不产生网络请求，外部重试不增加全文请求次数，普通日志不包含正文。
