# 保守查询改写与多查询融合设计

日期：2026-08-29  
状态：已确认，待实施

## 目标

解决用户问题与原文表达不一致，或主体、关系等隐含约束没有被现有检索器充分识别时，关键证据
虽进入候选却排名靠后的问题。第一版保留用户原问题，并由本地模型生成一条语义等价的保守改写，
两路独立召回后融合，再始终使用原问题统一重排。

真实语料试验中，问题“作者的职业身份经历过怎样的变化？”对应证据在分层检索中排名第 5；
改写为“作者本人先后担任过哪些职位？”后升至第 1。与此同时，“文中第一人称‘我’的职业
经历如何变化？”使证据降至第 9，说明改写可能改善召回，也可能引入噪声，不能替换原问题或
无约束地增加查询数量。

## 非目标

本次不实现：

- 问题拆解、HyDE 或假设答案生成；
- 检索证据充分性判断、自动多级路由或降级机制；
- 根据首轮候选反向生成查询；
- 多轮对话中的指代消解；
- 动态插件发现、注册中心或通用工作流引擎；
- 未经评测就把查询改写设为默认路径。

## 方案选择

采用“原问题为主、保守改写为辅”的多查询检索：

```text
当前用户问题 -> QueryRewriter -> 0..N 条保守改写

原问题 ---------> 当前 Retrieval Profile 召回 --+
                                                   +-> 去重 -> 加权 RRF -> 候选上限
保守改写 1..N --> 当前 Retrieval Profile 召回 --+                         |
                                                                             v
                                                            用原问题统一 Reranker
```

不采用改写直接替换原问题，因为改写一旦偏移会丢失原始意图；不采用候选分数直接相加，因为不同
查询的分数尺度不可稳定比较；不对每个查询分别重排，因为成本随改写数量增长，而且坏改写会获得
独立的最终判断权。

查询改写位于 Retrieval Profile 之上，同时支持默认 TopicChunk 路径和显式启用的父子分层路径。
因此可以分别评测切块方案与查询改写的独立贡献。

## QueryRewriter 边界

新增普通、显式的 `QueryRewriter` 接口，不建设动态插件系统。接口输入只包含：

- 当前用户问题；
- 本次允许返回的最大改写数量。

接口输出包含：

- 0 到 N 条改写文本；
- 成功、部分成功或失败状态；
- 实现与模型标识；
- 改写耗时和不含模型原始响应的简短诊断。

原问题不属于改写器输出，由检索编排层无条件保留。第一版提供：

- `OllamaQueryRewriter`：复用项目现有本地 Ollama 模型；
- `NoopQueryRewriter`：关闭改写，便于基线测试。

未来可增加规则或外部实现，通过显式配置工厂选择即可。不得因为 Ollama 失败而自动调用外部
服务；外部实现仍需显式启用并在调用前提示用户查询会外发。

第一版改写器只读取当前问题，不读取对话历史、付费语料、话题概括或检索候选。这样可独立评测
改写质量，并避免错误候选反过来污染查询。

## 保守改写约束

改写必须保持问题语义和答案范围。允许：

- 明确原问题已有的主体，例如将“作者”表达为“作者本人”；
- 明确所求关系或答案类型，例如将“身份如何变化”表达为“先后担任哪些职位”；
- 调整语序、补足省略成分和使用常见同义表达。

禁止：

- 补充原问题没有的人名、职位、时间、原因、结论或候选答案；
- 改变否定关系、比较对象、时间范围或问题所指主体；
- 利用常识猜测语料内容；
- 把单个问题拆成多个子问题。

Ollama 输出必须符合 JSON Schema，只返回改写列表，不返回解释。应用层确定性过滤空文本、首尾
空白、重复项、与原问题完全相同的文本和超过数量上限的结果。语义忠实度第一版由约束 Prompt
和冻结评测控制，不额外调用第二个模型验证，避免在尚无证据时增加延迟和复杂度。

## 配置与启用

配置保留清晰的实验参数：

```yaml
query_rewrite:
  provider: ollama
  max_variants: 1
  original_weight: 1.0
  rewrite_total_weight: 0.7
```

`max_variants` 第一版默认 1，并允许在受校验的上限内调整为多条；设置为 0 时等价于不生成改写。
无论实际返回多少条，所有改写共享 `rewrite_total_weight`，每条得到
`rewrite_total_weight / 有效改写数`，避免增加改写数量后淹没原问题。

第一版不改变现有默认搜索。CLI 通过 `--rewrite` 显式启用，`search`、`ask` 和 `eval run` 使用
同一套配置和编排逻辑。配置选择实现和参数，命令行开关决定本次是否执行实验。

## 召回、融合与重排

每个查询变体使用相同 Retrieval Profile 和相同召回深度，运行至 Profile 内部召回融合结束，
但不分别执行 Reranker。编排层随后：

1. 按统一候选 ID 合并各查询结果；
2. 以各查询内的候选排名执行带权 RRF；
3. 按融合排名截取受配置约束的统一候选上限；
4. 使用用户原问题执行一次现有本地 Reranker；
5. 按现有流程组装上下文并生成回答。

默认 Hybrid 路径仍先完成其 BM25、Dense 与 Profile 内 RRF；分层路径仍完成父、子层召回和子块
归一化。查询级加权 RRF 只融合各完整 Profile 的候选排名，不直接混合 BM25、Dense、父层、
子层或不同查询的原始分数。

候选应保留每个命中查询的类型、查询序号、Profile 内排名以及查询级融合排名。普通展示无需暴露
全部诊断，结构化搜索输出和评测运行需可审计这些信息。最终引用仍只来自规范正文。

## 失败处理与隐私

以下情况视为改写失败而不是检索失败：

- Ollama 不可用、启动失败或超时；
- 输出不符合 Schema；
- 所有结果都在确定性过滤中被丢弃；
- 只返回少于请求数量的有效改写。

这些情况记录状态和简短原因，使用原问题继续检索，不静默调用其他 provider，也不把普通检索
中断。只有索引不可用、检索执行失败等原有系统错误才沿现有错误路径终止。

改写默认在本地执行，输入不含付费正文。普通日志不得记录模型原始请求与响应；评测产物可以保存
原问题、经过校验的改写文本、配置、模型标识、状态和延迟，以支持复现。

## 评测与完成门槛

先使用现有 6 题冻结试验集做四组冒烟比较：

- TopicChunk；
- TopicChunk + 查询改写；
- 分层检索；
- 分层检索 + 查询改写。

然后使用约 20 道带人工确认支持段落的冻结评测集决定是否允许默认开启。除 P@K、Recall@K、
MRR、nDCG 和原子证据覆盖外，还必须报告：

- 每题正确证据排名的提升、持平和下降；
- 改写为空、重复、无效及失败的比例；
- 改写耗时、检索耗时和总延迟；
- 原路径本已正确、加入改写后发生明显退化的案例；
- 不同 QueryRewriter 实现、模型和 Prompt 版本。

第一版完成门槛是：开关关闭时现有行为不变；两种 Retrieval Profile 均能显式启用改写；改写
失败可靠退回原问题；多查询权重不随改写数量膨胀；评测能区分改写带来的提升、退化和成本。
是否改为默认开启属于后续独立决策，不由单个成功案例决定。
