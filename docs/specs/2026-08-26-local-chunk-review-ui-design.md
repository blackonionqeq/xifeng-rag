# 本地分块审核界面设计

日期：2026-08-26

## 目标

为单篇文章的待审核分块提案提供一个最小、本地、可视化的人工审核界面，使用户能在长文中直观看到原子单元和话题块，调整边界与检索字段，并保存一份可继续审核的草案。

第一版解决单篇人工审核到可搜索索引的闭环，不在网页中重新实现模型调用。模型切换、
自定义 Prompt 和单篇重试继续使用现有 `chunks retry`，从而保留完整文章外发前的命令行
披露与逐次确认。

## 启动方式与边界

新增命令：

```powershell
xifeng chunks review <ARTICLE_VERSION> --proposal <PROPOSAL_ID>
```

命令验证文章版本与提案均存在、互相匹配且提案处于 `pending_review` 后，在随机可用端口启动只绑定 `127.0.0.1` 的临时 HTTP 服务，并输出、默认打开带一次性随机令牌的本地 URL。进程持续运行直至用户按 Ctrl+C 退出。

可提供 `--no-open`，用于只打印地址而不自动打开浏览器，便于测试和无图形环境使用。第一版不支持监听局域网地址，也不提供固定免验证令牌。

## 页面与交互

页面采用单页布局：

- 左侧显示带连续编号的原子单元和所属话题块，保留正文换行，便于判断语义边界。
- 右侧显示按顺序排列的话题块卡片，包括范围、标题、摘要、关键词和 `include_in_index`。
- 用户可在相邻原子单元之间选择新边界，也可通过“与上一块合并”和“在此拆分”完成相同操作。
- 调整边界只改变原子单元归属，不修改规范正文，也不允许跳过、复制或重排原子单元。
- 标题、摘要和关键词可完全编辑；关键词在页面中使用简单的逗号分隔输入。
- `include_in_index` 可逐块开关。不索引块仍保留在草案及覆盖校验中，以保证批准清单能够审计完整文章结构。
- 每张话题块卡片提供“定位此块”按钮。点击后，左侧自动滚动到该块首个原子单元，
  并高亮该块范围内的全部原子单元；定位其他块时清除原高亮。定位状态只影响浏览器显示，
  不进入草案数据。

页面只加载命令指定的一个提案，不提供全库浏览、批量操作或多篇文章切换。

草案成功保存后，页面启用“批准并更新索引”按钮。点击按钮先显示浏览器确认框，明确列出
总分块数、进入索引块数、排除块数，以及批准清单不可修改。用户确认后才请求服务端执行；
未保存的页面修改会重新禁用该按钮，必须先再次保存草案。

## 数据流与保存

服务端从 SQLite 读取文章、版本、原子单元和原始提案。浏览器只与本机回环地址通信：

```text
SQLite 待审提案 + 原子单元
        -> 本地只读加载接口
        -> 浏览器内编辑
        -> 本地草案保存接口
        -> data/reviews/*.draft.json
        -> 用户二次确认
        -> 批准不可变清单
        -> 原子构建并切换活动索引
```

保存草案时，服务端不信任浏览器提供的正文或身份字段。它固定使用启动时选定的 `proposal_id`、`article_version` 和数据库中的 `canonical_content_hash`，只接受用户可编辑的话题列表。

保存前复用现有 Pydantic 模型与 `validate_topic_coverage`，验证：

- 范围从 1 开始并覆盖到最后一个原子单元；
- 相邻块连续，且无重叠、缺口或倒序；
- 标题、摘要、关键词及布尔字段符合现有 Schema；
- 至少保留一个 `include_in_index: true` 的块，以确保草案后续可以通过现有批准校验。

草案写到与审核导出文件同目录，命名为：

```text
<VERSION>.<PROPOSAL>.draft.json
```

写入采用同目录临时文件加原子替换。重复保存覆盖这份草案，但不覆盖模型生成的 `.review.json` 和 `.review.md`，也不修改数据库中的提案。保存成功后页面显示明确的文件路径和时间。

批准接口只读取当前审核会话最后一次成功保存的草案文件，不接受浏览器再次提交话题正文。
它复用现有 `approve_manifest`，在独立数据库事务中生成不可变清单与 `TopicChunk`，然后复用
现有 `build_index` 构建全体已批准文章的新索引。构建成功前旧活动索引继续可用；成功后再
原子切换活动索引。现有 `chunks approve` 与 `index build` 仍作为可恢复的命令行入口保留。

## 服务结构

新增一个聚焦的审核服务模块，职责分为：

- 读取并验证指定待审提案，组装不含额外数据库能力的页面数据；
- 渲染自包含的 HTML/CSS/JavaScript 页面；
- 处理当前会话的只读加载、草案保存及批准并更新索引请求；
- 校验一次性令牌、请求体大小和内容类型；
- 在退出时关闭 HTTP 服务。

第一版使用 Python 标准库 HTTP 服务与原生浏览器 API，不新增 FastAPI、模板引擎或前端构建链。HTML、CSS 和 JavaScript 分别保存为包内静态文件，由审核服务模块加载；Python 业务校验与页面脚本保持分离，以便后续替换 Web 框架而不改变审核数据结构。

## 安全与隐私

- 服务器固定绑定 `127.0.0.1`，不接受配置覆盖为外部地址。
- 每次启动生成高熵随机令牌，所有读取与保存请求都必须携带；令牌只存在于进程内。
- 页面不得加载 CDN、字体、统计脚本或任何远程资源。
- 设置严格的 Content Security Policy，只允许同源脚本、样式和请求。
- 服务端不记录正文、请求体或完整草案内容；终端只输出服务地址、保存结果和无正文错误信息。
- 不新增外部网络请求。浏览器访问仅发生在本机回环接口。
- 退出服务后令牌失效；重新启动会产生新令牌。

## 错误处理

- 文章版本、提案不存在或不匹配：启动前失败，不开启端口。
- 提案不是 `pending_review`：拒绝启动，避免编辑已批准或失败的提案。
- 非法令牌、非 JSON、过大请求或错误 Content-Type：返回明确的 4xx，且不写文件。
- 覆盖校验失败：返回逐项校验信息，浏览器保留当前编辑内容供修正。
- 草案写入失败：保留原草案，页面提示失败，不修改数据库。
- 未成功保存草案或未携带明确确认字段：拒绝批准请求。
- 批准失败：不启动索引构建，并保留待审状态供用户修正。
- 批准成功但索引失败：批准清单保持有效，旧活动索引继续服务；页面明确显示部分成功，
  并将按钮变为“重试更新索引”。重试不得创建第二份批准清单。
- 批准和索引均成功：页面显示清单 ID、活动索引 ID 和块数，禁用所有编辑与保存控件。
- 端口或浏览器打开失败：端口失败则退出；浏览器打开失败不终止服务，用户仍可复制终端地址。

## 测试与验收

单元测试使用自造短文本和临时 SQLite，不读取真实付费文章。至少覆盖：

- 正确组装指定 proposal 的文章、原子单元和话题数据；
- 错误 version/proposal、非待审状态在启动前被拒绝；
- 合法边界、合并、拆分和字段编辑后的草案可以保存；
- 定位话题块会滚动并只高亮其当前范围，不改变待保存的话题数据；
- 缺口、重叠、越界、空索引和非法字段被拒绝；
- 无令牌或错误令牌无法读取正文或保存草案；
- 保存使用原子替换且不覆盖 `.review.json`；
- 页面不引用远程资源；
- 保存草案本身不会创建 `approved_manifests`、`topic_chunks` 或索引文件；
- 未确认的批准请求被拒绝；确认后的请求生成一份清单并切换新活动索引；
- 索引构建失败时旧活动索引保持有效，并可在同一页面重试；
- 成功后页面禁止继续编辑已成为不可变清单的提案。

人工验收使用自造或专门保留的待审提案：确认可快速定位边界、把文末目录块设为不索引、
修改字段、保存草案，并在确认摘要无误后批准和更新索引。不得为了验收重复批准已有清单。

## 非目标

第一版不包含：

- 模型选择、自定义 Prompt 或重试任务；
- 撤销批准、修改已批准清单或只构建单篇文章的独立索引；
- 多用户、远程访问、账户与权限系统；
- 多篇文章批量审核；
- 拖拽排序、自动保存、历史版本或多人协作；
- FastAPI、React/Vue 或前端构建工具链。

后续只有在本地单用户审核流程稳定后，才考虑把模型重试移入页面或引入正式 API 层。
