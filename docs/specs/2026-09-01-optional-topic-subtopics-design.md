# 可选细话题与既有文章补充设计

状态：已确认，2026-09-01。

## 1. 目标

在现有人工批准的顶层 `TopicChunk` 下增加可选细话题，保存用户可能单独记住的具体案例、
局部概念、机制或特殊表述，改善“记得内容但忘了文章”的文章反查。

细话题不是新的正文分块，不要求覆盖全文，不参与作者原话引用，也不能改变已经批准的分块
边界。文章没有细话题时，原有分块、批准、证据索引和文章反查流程必须保持可用。

## 2. 数据结构与生命周期

每个细话题只包含三个用户可编辑字段：

```text
title
start_unit / end_unit
summary
```

它必须归属于一个已批准顶层话题，范围必须位于父话题范围内；同一父话题内允许不连续覆盖、
留空或没有任何细话题。标题与概括属于 AI 生成的检索辅助信息，单元范围只用于回到规范正文。

批准的分块清单继续不可变。细话题使用独立、可替换的补充记录：

```text
ApprovedManifest / TopicChunk（不可变分块）
  -> SubtopicProposal（待审草案）
  -> ApprovedSubtopicSet（当前批准补充）
```

重新生成只创建新草案；新草案批准成功后原子替换该文章版本当前活动的细话题集合。失败或放弃
草案不得清空已有批准结果。结构化状态保存在 SQLite，稳定关联使用文章版本、批准清单和父话题
范围，不依赖绝对路径。

## 3. 新文章联合生成

今后的 AI 分块结构化输出在每个 `topics[]` 下允许返回 `subtopics[]`：

```json
{
  "end_unit": 196,
  "title": "顶层话题",
  "summary": "块级概括",
  "keywords": ["关键词"],
  "subtopics": [
    {
      "title": "AI扁平化",
      "start_unit": 142,
      "end_unit": 196,
      "summary": "AI替代中间信息处理层，留下资本增值绕不开的人。"
    }
  ]
}
```

默认本地模型和用户逐次确认的单篇外部分块重试都在原有完整正文请求中并列生成，不增加第二次
全文请求。Prompt 明确要求只选择有辨识度的案例、概念、机制和特殊表述，不把每句话重新概括
一遍。每个父话题允许为空，也不设业务数量上限；相邻、范围重叠或表达同一机制的候选必须
合并，并只保留有检索辨识度的候选。细话题范围原则上不少于 10 个原子单元，不足时应并入
相邻或同机制的细话题，无合适合并对象且辨识度不足时直接丢弃。整篇文章同样不设细话题总数
上限，使细话题数量可以随文章长度和顶层结构自然增长。结构化 Schema 仍保留每父话题最多
20 个的异常输出保护；这是安全边界，不是生成目标，索引阶段也不截断已批准结果。

顶层分块继续执行严格连续覆盖校验。细话题只执行宽松校验：允许字段缺失或空数组；非法范围、
空标题或空概括形成非阻断诊断，不得导致本来合法的分块提案重试或失败。审核页允许用户忽略、
编辑或删除全部细话题；批准分块时，有效细话题作为第一版补充集合一并批准。

旧提案和旧审核 JSON 允许完全没有 `subtopics`，不回填、不迁移为失败状态。

## 4. 既有文章补充

语料管理页对已有批准分块的活动文章提供“补充细话题”操作，并显示三种状态：未补充、待审核、
已批准。点击后先展示文章标题、版本、清洗后字符数、原子单元数、provider、模型和最大完整
请求次数，再按现有隐私规则确认。

模型输入为该文章的批准父话题边界、标题以及带原编号的规范正文，只允许提取细话题，不能修改
父边界、父标题、父概括或关键词。默认只处理 `include_in_index=true` 的父话题。一次调用处理
一篇文章，不提供批量确认或自动回填。补充生成与新文章联合生成使用相同的规则：父话题和
整篇文章都不设业务数量上限，合并相似候选，细话题范围原则上不少于 10 个原子单元，并保留
每父话题 20 个的 Schema 安全边界。

生成成功后进入独立细话题审核页。该页面可以复用现有审核页的原文单元和卡片组件，但标题与
动作必须明确说明“补充细话题，不会修改现有分块”。批准后只发布文章反查索引；证据块索引和
引用链不变。

## 5. 文章反查定位

首版将批准细话题的标题和简短概括加入现有单篇文章检索文档，并在结果中展示与查询匹配的细
话题。文章整体概括、顶层话题和关键词继续保留；Profile 版本必须升级，旧 Build 保持不可变，
便于与现有基线对照。细话题为空的文章生成与当前相同的检索文本。

首版不建设逐细话题向量和文章聚合。若评测发现单篇长文本稀释 Dense 表示，后续再以独立
Profile 实验“逐细话题召回后按文章聚合”，并显式处理长文章因细话题更多而获得更多命中机会
的偏置。

## 6. 上下文与失败处理

当前 Codex CLI 默认模型为 `gpt-5.6-terra`。本机 Codex 模型缓存报告 272,000 token 上下文、
95% 有效窗口（258,400 tokens）；当前活动语料最长规范正文约 23,571 字符，目标文章约 17,477
字符。首版不因理论估算拆分请求，而通过真实单篇验收验证。

程序仍需把字符数、单元数、模型和最大请求次数放入外发披露。Codex 返回上下文超限、结构化
输出失败或超时时，草案失败且不影响现有批准分块或细话题集合；不得自动拆篇外发或增加未披露
的请求次数。

## 7. 隐私与引用

- 默认生成与审核保持本地；Codex CLI 仍属于完整文章外发例外。
- 每次 Codex 调用必须按单篇、provider、模型逐次披露并确认。
- 不在普通日志、数据库或 Git 保存完整请求、外部原始响应或付费正文副本。
- 细话题标题和概括不是作者原话，不能作为回答引用。
- 回答与引用仍只使用规范正文 `original_text` 及稳定原子单元范围。

## 8. 验证

至少验证：

1. 新 Schema 兼容没有细话题的旧输出；
2. 细话题空缺或局部非法不阻断合法顶层分块；
3. 有效细话题只能位于父话题范围内；
4. 新文章联合提案能够审核并批准细话题；
5. 既有文章按钮只创建补充草案，不修改批准分块；
6. 重新生成失败时旧批准细话题继续可用；
7. 批准补充只更新文章反查索引；
8. 默认路径不产生网络请求，Codex 路径保留逐次披露确认；
9. 用自造短文本验证检索聚合和长文章细话题数量偏置；
10. 用用户指定文章完成一次真实 Codex 结构化输出验收，不把正文或输出提交 Git。
