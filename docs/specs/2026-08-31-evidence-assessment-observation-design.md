# 证据充分度观测层设计

状态：已确认，进入实现。

## 背景与目标

当前 6 题试验表明，保守查询改写能改善普通 TopicChunk 检索，但与分层检索组合时可能退化。
系统暂时没有足够样本建立可靠的问题分类路由，也不能根据单个成功案例决定默认策略。

第一阶段在 Reranker 与上下文组装之间增加一个只观测的证据评估层。它记录最终候选呈现出的
确定性信号，帮助后续验证“证据不足时补跑分层检索”的降级假设。评估层默认关闭，不改变
候选排序、上下文、回答或网络行为。

本阶段不做：

- 不输出“证据充分”或“证据不足”结论；
- 不自动切换 TopicChunk、分层检索或查询改写；
- 不用模型判断问题约束是否被覆盖；
- 不建设评估器插件注册表、工作流引擎或单独数据库表。

## 组件边界与数据流

评估器是无网络、无持久化副作用的本地纯函数：

```text
召回 -> 融合 -> Reranker -> 最终 Top-K 候选 -> EvidenceAssessor -> 上下文组装
                                              |
                                              +-> EvidenceAssessment
```

```python
assess_evidence(
    candidates: Sequence[RetrievalCandidate],
    observation_k: int,
) -> EvidenceAssessment
```

低层 `search*` 函数继续返回 `list[RetrievalCandidate]`。`search`、`ask` 和 `eval run` 的编排层
在拿到最终排序候选后调用同一评估器，避免把评估逻辑散落到各入口，也避免为了观测功能重写
检索接口。

评估器只观察实际准备交给上下文组装的前 `observation_k` 个候选。它不读取正文内容，不调用
Embedding、Reranker 或 Generator。输出包含固定的 `calculation_version`，以后修改公式时可以
区分历史评测结果。

## 第一阶段指标

`EvidenceAssessment` 包含 `status`、`calculation_version`、`observation_k`、实际观察数量和以下
指标：

- `candidate_count`：调用方提供的最终候选总数；
- `article_count_at_k`：观察范围内不同文章 ID 数；
- `top1_reranker_score`：第一名的 Reranker 分数；
- `top1_top2_margin`：第一名减第二名的 Reranker 分数；
- `top1_top3_margin`：第一名减第三名的 Reranker 分数；
- `top1_dual_retrieval`：第一名是否同时包含 Dense 与 BM25 来源；
- `dual_retrieval_rate_at_k`：观察范围内同时包含 Dense 与 BM25 来源的候选比例；
- `shared_by_original_and_rewrite_rate_at_k`：观察范围内同时被原问题和至少一个改写召回的候选
  比例；
- `top1_shared_by_original_and_rewrite`：第一名是否同时被原问题和至少一个改写召回。

比例以实际观察候选数为分母。未启用或没有相应阶段时不伪造零值：没有 Reranker 分数时分数与
分差为 `null`；候选不足两个或三个时相应分差为 `null`；没有有效改写痕迹时两项改写一致性
指标为 `null`。没有候选仍是成功计算，`candidate_count=0`，其他无定义指标为 `null` 或零个
文章。

第一阶段不计算问题约束覆盖。该指标需要额外语义分析，会把本应可解释的观测层变成另一个模型
判断器；只有确定性信号经更大评测集证明不足时再单独设计。

## 配置与入口行为

配置新增：

```yaml
evidence_assessment:
  enabled: false
  observation_k: 5
```

- 关闭时不计算、不展示、不保存评估结果，现有命令输出和业务行为保持不变；
- 开启时，`search` 输出候选与结构化 `evidence_assessment`；
- 开启时，`ask` 在外部 Generator 调用前向用户显示简短评估诊断，但不改变证据或回答；
- 开启时，`eval run` 在现有逐题 `details_json` 中保存评估结果，并对可用数值或布尔指标汇总
  有效样本数、均值、中位数、最小值和最大值；
- 普通 `search` 和 `ask` 不写数据库，冻结评测继续使用现有评测运行记录，不新增迁移。

后续确认指标与阈值有效后，可以独立把 `enabled` 默认值改为 `true`。自动补跑分层检索必须使用
另一个明确配置，不能暗中改变观测开关的语义。

## 失败与隐私

评估属于诊断辅助，不能成为检索或回答的新增单点故障。计算异常时返回 `status=failed` 和不含
问题、正文、候选文本的简短诊断；主流程继续使用原候选。实现应尽量用完整枚举和局部空值处理，
使正常的缺失阶段不会被当作异常。

评估结果只包含计数、分数、比例、布尔值、状态和版本，不复制原问题或付费正文。它不会新增
网络请求，也不会改变 Generator 的外发范围。

## 验证与后续实验

自动验证覆盖：

- 完整候选、空候选、候选不足和缺少 Reranker 分数；
- Dense/BM25 单路与双路来源；
- 原问题/改写共同命中、仅单路命中和未启用改写；
- 开关关闭时 `search`、`ask`、`eval run` 行为不变；
- 三个入口使用同一计算结果，评测汇总忽略 `null` 并记录有效样本数；
- 评估失败不阻断主流程，结果与普通日志不包含新增正文副本。

实现后先对现有 6 题、职业经历已知失败题和少量人工问题运行观测。只比较指标分布与人工确认的
检索成败，不在该样本上直接固化阈值。扩充到约 20 题后，再决定是否设计“证据不足时补跑分层
检索”的判定与降级机制。

### 首轮观测结果

实现后的 6 题 TopicChunk + Hybrid + Reranker + Query Rewrite 运行
`eval_1ba6c9f3cddc88d63b45898c5dc360a8` 中，6 次评估均成功。Top1 Reranker 分数范围为
0.080–0.967，Top1/Top2 分差范围为 0.057–0.681；一次查询改写失败并回退原问题，不影响评估。

职业经历问题在 TopicChunk 路径上的 Top1 分数为 0.0111、Top1/Top2 分差为 0.0003，原问题与
改写的最终候选共有率为 0，且首名错过目标段落。补跑分层检索后，目标子块升至第 1 名，说明
这些低置信信号有机会识别值得降级的案例。

但 6 题中 Top1 分数最低的题目（0.080，分差 0.057）在既有分层对照中反而由正确证据第 1 名
降至第 3 名。因此第一阶段指标只能提示“不确定”，不能直接决定用分层结果替换 TopicChunk
结果；后续降级设计需要补跑后合并或比较两路证据，并继续扩大人工标注样本。职业经历题在分层
命中正确证据后 Top1 绝对分数仍只有 0.0251，也进一步说明不能用单一绝对阈值判定充分性。
