# 语义原子单元与内容角色设计

状态：已确认，作为 V0 语义分块设计的第二份增补。

## 1. 实测问题

语义优先提示词在真实短文和长文上均能生成合法提案，但暴露了两个不同问题：

- 短文中的付费提示、阅读提示或其他非实质内容也必须被分块，且可能被模型各自提升为
  独立话题；
- 当前解析器以 Markdown 空行划分原子段落。部分抓取文件大量使用单行换行，导致首个
  空行前的 257 行被合并为一个 13,029 字符的不可分割段落。

提示词只能在程序提供的原子边界间选择，无法修复第二个问题。内容噪声也不能通过
“允许模型漏掉段落”处理，否则会破坏完整覆盖与审计能力。

## 2. 设计目标

1. 给语义模型提供足够细、具有稳定源位置的候选边界；
2. 最终话题块仍按语义形成，不使用固定字数或固定块数；
3. 所有规范内容继续被提案完整覆盖；
4. 明确的付费提示、导航和推广内容可以保留但不进入检索索引；
5. 对内容角色存在歧义时默认保留，不能让模型静默删除作者论述；
6. 清洗规则升级产生新文章版本，不覆盖已批准的旧版本和实验。

## 3. 原子单元解析

原先“空行之间为一个段落”的规则升级为两级确定性切分：

1. 每个非空物理行首先成为候选单元；
2. 单行内含有多个中文句子时，在 `。！？；` 及其后的闭合引号处继续切分。

英文问号、感叹号和分号同样作为句末边界；英文句点暂不作为通用边界，避免拆开 URL、
小数和缩写。Markdown 标题、独立链接行和不能安全拆分的行保持为单个单元。

句子或短行只是供模型选择边界的原子单元，不是最终检索块。程序不按字符数合并或拆分
最终话题块。极短单元由模型与相邻内容组成同一个语义块，因此不会直接造成碎片化索引。

每个原子单元保存准确的 `source_start` 和 `source_end`。Markdown 链接仍保留锚文本并
单独记录 URL；外部源文件保持只读。

清洗器版本升级。扫描时不能仅凭源文件哈希相同就跳过；只有源文件哈希和清洗器版本都
相同才可复用。清洗器升级为每篇文章生成新版本，旧批准版本在新版本批准并完成索引前
保持可用。

## 4. 语义边界输出

模型不再负责重复计算每块起点。新提案中的每个话题只返回：

```json
{
  "end_unit": 42,
  "title": "安全周期与仓位原则",
  "summary": "作者说明……",
  "keywords": ["安全周期", "仓位"],
  "content_role": "substantive"
}
```

程序按顺序推导第一块从单元 1 开始，后续块从上一块终点加一开始。结束单元必须严格
递增，最后一个结束单元必须等于全文单元数。程序不猜测或修改模型选择的结束边界。

该格式减少 4B 模型在大量编号单元上填写冗余起点时产生的覆盖错误。领域层仍可在导出
审核文件前将结果规范化为现有的起止范围，存储和引用结构无需另建一套。

## 5. 内容角色

每个完整覆盖的语义块必须标记以下角色之一：

- `substantive`：作者的观点、论证、案例、叙事铺垫、必要过渡或其他可能影响理解的内容；
- `boilerplate`：明确的付费提示、阅读操作提示、文章导航、账号推广或与文章论述无关的
  固定样板内容。

提示词采用保守规则：只要不能确定是样板内容，就标记为 `substantive`。不能因为内容
简短、口语化、重复、像“废话”或不是核心结论就自动排除；作者的引言、故事和论证铺垫
仍属于正文。

模型应将相邻的 boilerplate 合并为尽量少的块，不能把每句提示分别建立话题。

## 6. 审核与索引

JSON 和 Markdown 审核产物展示每块的角色。用户可以修改边界、标题、概括、关键词和
角色，批准时仍验证全文恰好覆盖一次。

`approved_manifests` 增加可空的 `topics_json` 字段。新批准清单在此保存人工修改后的
全部规范化块及角色，用于审计；该字段通过向前迁移加入。已有清单保持不变，不虚构其
当时未保存的人工编辑内容。只有 `substantive` 块生成可检索的 `TopicChunk` 并进入
BM25；`boilerplate` 原文仍存在于规范文章版本和新批准清单中，但不会作为作者观点被
召回或引用。

为了兼容已经导出的旧审核文件，缺少 `content_role` 的旧话题按 `substantive` 处理。
新模型 Schema 必须显式返回角色。

若一篇文章被全部标记为 boilerplate，批准失败并要求人工检查，不能建立空文章索引。

## 7. 提示词约束

新提示词要求：

- 先识别少量明确 boilerplate，再按完整观点和论证阶段组织 substantive 话题；
- 阅读提示、付费说明、单句转折不能被提升为独立 substantive 话题；
- 一个 substantive 话题应包含相对完整的观点、论证、案例或叙事阶段；
- 相邻内容属于同一连续论证时合并，不因原子单元很短而拆分；
- 不预设块数或字符数；
- 只返回结束单元及检索辅助字段，不复制原文。

Prompt 与 Schema 版本同时升级，生成新的提案 ID。旧提案和批准清单保持不可变。

## 8. 验证

自动化测试至少覆盖：

1. 单行换行能够生成独立、连续且源位置准确的原子单元；
2. 长行按中英文句末标点拆分，但 URL、小数和普通英文句点不被误拆；
3. 链接锚文本和 URL 元数据在新切分下保持正确；
4. 清洗器版本变化时，即使源哈希未变也生成新文章版本；
5. 结束单元严格递增并完整覆盖时可推导连续起止范围；
6. 越界、倒序或未覆盖全文的结束单元被拒绝并安全重试；
7. 新 Schema 要求 `content_role`，旧审核文件缺失角色时兼容为 substantive；
8. boilerplate 保存在批准清单但不生成 TopicChunk；
9. 全部为 boilerplate 的审核文件不能批准；
10. BM25 只包含 substantive 块；
11. 数据库迁移后，新批准清单保存人工修改后的完整话题与角色 JSON。

真实验收继续使用同一篇短文和长文，对比调整前后的原子单元数、语义块边界、
boilerplate 标记、人工修改量和生成耗时。两份新提案只导出审核，不自动批准。
