# DeepSeek Generator 设计

状态：已确认，进入实现。

## 1. 目标与范围

在现有 Hybrid 检索、本地 Reranker 和确定性上下文组装之后，增加第一版交互式回答生成。
Generator 只处理单轮问题，使用组装后的少量证据生成可验证、可拒答的结构化回答。

第一版只实现 DeepSeek API 适配器，不实现本地 Generator、多轮对话、联网事实补充、独立模型
审查调用或通用 provider 注册系统。单篇问答与跨文章综合共用同一协议。

## 2. 核心数据流

```text
当前问题
  -> Hybrid 检索
  -> 可选本地 Reranker
  -> 确定性上下文组装
  -> 无证据时本地拒答
  -> 展示外发摘要
  -> DeepSeek 单次结构化生成
  -> 本地结构与引用校验
  -> 必要时最多一次修复请求
  -> 确定性渲染最终回答
```

`Generator` 只接收当前问题、`AssemblyResult` 产生的证据上下文和补充分析策略。它不能重新
检索、重新排序、修改证据或扩大外发范围。DeepSeek 的服务地址和模型 ID 使用显式配置，
不在业务代码中绑定永久模型名称。

用户执行回答命令本身视为显式触发外部生成。发送前必须展示服务地址、模型、证据块数量、
证据字符数和最大外部请求次数，但不额外要求机械式 `y/N` 确认。发送完整单篇文章的既有
特殊流程仍保持逐次二次确认。

## 3. 证据边界与补充分析

回答分为两个来源边界清晰的部分。

### 3.1 基于语料的回答

该部分可以复述原文，也可以对一条或多条证据进行归纳、比较和推理。每个主要结论必须绑定
本次上下文中存在的证据 ID，并区分：

- `source_statement`：资料明确表达的内容；
- `inference`：模型依据资料作出的归纳或判断。

Generator 不得把推断伪装成作者原话，也不得使用模型自身知识填补语料中的事实缺口。

### 3.2 模型补充分析

补充分析使用三态策略：

- `auto`：默认值；只有问题明确要求评价、建议、预测或模型观点时才生成；
- `on`：用户强制开启；
- `off`：用户强制关闭。

补充分析可以提供评价框架、可能影响、反例、风险和建议，但不能凭模型记忆引入具体数据、
事件、引文或他人观点。它必须独立展示并声明不完全来自本地语料，不能附加语料证据 ID，
也不能写成作者观点。补充分析不能用来掩盖或填补语料回答的证据不足。

未来若增加联网检索，带外部来源的事实应作为新的来源类型单独设计，不能混入该字段。

## 4. 结构化回答协议

Generator 返回经过 Pydantic 建模的结构化结果，概念结构如下：

```text
status
grounded_sections[]
  text
  statement_type
  evidence_ids[]
supplementary_analysis
limitations[]
```

`status` 只有三种：

- `answered`：核心问题得到充分回答；
- `partially_answered`：只能回答问题的一部分；
- `insufficient_evidence`：现有资料不能支持核心回答。

每个 `grounded_section` 必须包含非空文本、明确的 `statement_type` 和至少一个有效证据 ID。
`supplementary_analysis` 只有在策略允许时才能出现，且不得包含证据 ID。`limitations` 用于说明
缺少的资料、未覆盖的范围或无法确认的方面。

用户可见 Markdown 由本地程序确定性渲染。程序负责添加引用、来源说明、推断标签、模型补充
免责声明和限制信息，不能依赖模型自行遵守展示格式。

## 5. 校验与失败处理

- 组装结果为 `no_evidence` 时，本地直接返回 `insufficient_evidence`，不调用 DeepSeek。
- 有候选证据不代表必须回答；Generator 可以判断证据不相关或不足。
- `partially_answered` 只展示有证据支持的部分，并明确未回答的部分。
- 首次结果存在 JSON、Schema、状态一致性或证据 ID 错误时，允许携带精简校验错误进行一次
  修复请求；修复请求不得增加证据或改变外发范围。
- 若模型返回 `insufficient_evidence`，同时给出结构合法、引用有效的非空结论和非空限制，
  本地将其归一化为 `partially_answered` 并记录原状态；其他矛盾不得自动归一化。
- 一次问答最多两次外部请求，不启用隐藏的 SDK 自动重试，也不自动切换其他模型。
- 修复仍失败时明确报告生成失败，不能把未校验文本作为答案展示。
- API 超时、限流、余额不足、鉴权失败或服务故障均明确失败，不回退到其他外部或本地模型。
- 本地校验只能证明证据 ID 存在、字段关系合法，不能证明证据在语义上真正支持结论。语义
  忠实度通过 Prompt、冻结题集评测和人工抽查验证。

## 6. 隐私与可观测性

外部请求只包含当前问题、最终组装的少量证据和生成指令。不得发送未入选候选、完整文章、
AI 分块提示词或本地路径。

普通日志只允许记录 provider、模型、服务地址、证据数量、字符数、请求次数、耗时、回答状态
和错误类型。不得记录 API 密钥、问题原文、证据正文、完整渲染请求、外部原始响应或完整回答。
API 密钥继续只从进程环境变量或 Git 忽略的项目根目录 `.env` 读取，进程环境优先。

## 7. 配置与接口边界

第一版保留一个窄的 `Generator` 协议和一个 DeepSeek 实现。配置至少包括 provider、base URL、
model、timeout 和输出 token 上限；补充策略属于单次查询参数，不属于索引配置。

模型 ID 必须可配置，并可通过独立诊断命令调用服务商模型列表进行核对。模型或 Generator
Prompt 的变化不触发索引重建，但评测运行必须记录实际 provider、模型、Prompt 版本和参数。

## 8. 验证范围

自动化测试至少覆盖：

- 无证据时不产生网络请求；
- 三种回答状态及其字段一致性；
- `source_statement` 与 `inference` 的确定性渲染；
- `auto/on/off` 对补充分析的约束；
- 不存在、重复或空证据 ID 的拒绝；
- 一次成功、一次修复成功和修复后失败；
- 401、402、429、5xx 与超时不触发 provider 回退；
- 普通日志和持久化数据不包含问题、证据正文、完整回答或密钥；
- 单篇与跨文章证据使用同一输出协议。

第一版回答质量通过冻结题集和人工抽查评估，重点记录忠实度、主要结论引用覆盖、引用支持度、
拒答正确性、补充分析越界情况、延迟和失败案例。
