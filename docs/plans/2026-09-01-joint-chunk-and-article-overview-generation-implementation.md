# 新文章分块与整体概括联合生成实施计划

对应设计：[`docs/specs/2026-09-01-joint-chunk-and-article-overview-generation-design.md`](../specs/2026-09-01-joint-chunk-and-article-overview-generation-design.md)

## 交付顺序

1. 先扩展领域模型、保守 JSON Schema 与分块 Prompt，使尚无批准清单的文章在一次调用中返回
   `article_summary + topics[]`；保留旧 `TopicProposal` JSON 的读取兼容。
2. 在分块提案成功时创建绑定 `proposal_id` 的待审 `ArticleOverview`，保证同一提案重放幂等、
   并列重试互不复用，已有批准分块和既有概括不回填。
3. 扩展审核文档、草案 API 和前端，在话题编辑区上方展示整体概括；保存时一起校验 200 字上限，
   同一次确认在数据库中批准不可变分块清单和概括。
4. 扩展审核后的构建编排，依次发布证据块索引与文章级索引；分别报告结果，任何失败都保留对应
   旧活动 Build，并允许原审核会话幂等重试。
5. 为联合 Schema、默认/自定义 Prompt、持久化、旧数据兼容、同页编辑、联合批准、双索引成功与
   各自失败增加测试；所有夹具使用自造短文本。
6. 同步 README、总体架构、切块索引设计和既有文章概括设计，明确联合生成读取原文但文章索引
   仍只保存批准概括与派生元数据。
7. 运行定向 pytest、完整 pytest、Ruff、Pyright、`git diff --check` 与 CLI 帮助 smoke；确认普通
   日志不包含正文、外部重试不增加全文请求次数。

## 实现边界

- 联合路径只针对没有 `ApprovedManifest` 的文章版本；既有概括不迁移、不重写。
- 不新增第二次全文模型调用；外部 provider 继续复用现有单篇逐次确认。
- 新生成结果严格要求整体概括，旧提案和旧审核 JSON 允许缺少该字段。
- `ArticleOverviewRow` 继续作为概括事实来源，不把概括只藏在 `topics_json` 中。
- 分块与概括批准属于同一数据库事务；两个派生索引的发布各自保持原子性。
- 不引入后台任务、通用工作流、注册表或新的服务框架。
- `data/`、外部付费语料和无关 `tempnpm-cache/` 不提交。

## 完成门槛

- 新文章一次模型调用产生可审的分块与整体概括，审核页能一起编辑、保存和批准；
- 批准成功后，新文章立即可用于证据检索与文章反查；
- 旧提案、旧批准文章和现有独立概括流程行为不变；
- 双索引任一失败都不替换其旧活动 Build，重试不会产生重复清单或重复概括；
- 本地默认路径无网络请求，外部单篇重试仍只有既有确认过的全文请求；
- 完整自动化测试和静态质量检查通过，相关文档与实现一致。
