# 评测问题起草（eval-question-drafter）

为 `xifeng eval curate` 的人工出题环节起草候选。你不是在出阅读理解题，
而是在为检索评测建立**边界清楚、证据稳定、可判断检索质量**的金标准问题。
产出永远只是候选——真正的金标准必须经人工在 eval curate 工作台逐项审核。

## 核心思想（先读这个，再读步骤）

一条好题的本质：**两个独立阅读文章的人，大概率会标出相近的答案要点和证据**。
如果做不到这一点，题就是主观、宽泛或含有未说明前提的，写得再通顺也不能用。
生成每个候选时都用这个标准自检一次；阶段二输出前再自检一次。

为什么强调边界：V0 以 `top-k=5` 观察检索。**Top-K 的检索单元是话题块（一个
完整的 AI 生成话题段），不是原子句**。实际每个话题块约覆盖 60–150 个原子单元
（当前库中位数约 100）。一篇 600 单元的文章通常只有 5–7 个话题块，Top-K=5
意味着几乎取回整篇文章。因此单篇文章内的题目，证据超出 Top-K 容量的风险极小；
真正的难度来自**排名**：正确的话题块能否在 Top-5 里排进来，还是会被同文章其他
话题区的块压下去。证据散在十几个不连续位置、必须跨多个话题块才能覆盖的题，
低分只说明问题设计超出检索能力范围，不能说明检索系统失败——这种题测不出任何东西。

## 输入

参数是文章名。根据 `config.local.yaml`（或 `config.example.yaml`）中
`corpus.source_dir` 的实际值确认语料目录，文章名即该目录下的 md 文件名（去扩展名）。
不要把付费正文复制进任何会提交到仓库的文件。

## 第 0 步：导出规范编号正文

原子单元编号（eval curate UI 里的"段落号"）与原始 md 的段落结构不一致，
**必须以数据库中的编号为准**，否则证据范围对不上。运行项目虚拟环境中的导出脚本：

```powershell
& .venv/Scripts/python.exe .claude/skills/eval-question-drafter/scripts/export_units.py "<文章名>"
```

- 支持部分标题匹配；`--list` 列出全部文章；匹配到多篇时会打印候选清单。
- 若文章还没入库，脚本会报错——此时提醒用户先运行 `uv run xifeng corpus scan`，
  不要退回去直接读原始 md 来编段落号（编号会对不上）。
- 输出可能是几百上千行。分段读入，先通读把握全文结构（开头/各话题区/结尾），
  需要核对细节时再回到具体单元区间。长文建议按 200–300 个单元一段分批读。

## 第 1 步：通读理解（读完正文、出题之前）

不要读完就直接想题。先把对文章的整体理解写出来，回答完三个问题再进入阶段一：

1. **核心论点**：文章到底主张什么？1–3 句概括，不是罗列话题，
   而是作者想让读者接受的那个判断。叙事/随笔类文章没有严格论点时，
   写文章的主旨或核心观察。
2. **关键论据**：支撑核心论点的主要论证，每条标注落在哪个话题区、
   大致单元范围（如「第 40–75 单元：用某案例论证……」）。这份
   「论据—位置地图」就是阶段一挑证据区域的底稿，出题时对着地图选，
   不必重新通读全文。
3. **认同与不认同**：哪些论据你认为扎实、哪些薄弱或存疑，各附一句理由。

为什么加这一步：直接从「读完」跳到「出题」，注意力容易被局部段落吸走，
既慢又容易出成细节题。先写出论点与论据地图，出题挑的才是文章里
真正重要的东西。

「认同/不认同」直接服务出题质量，不只是批判性练习：
- 你都觉得论证薄弱、拿不准的论据，正是「两个独立读者标不出一致要点」
  的高危区，阶段一避开它们；
- 判断认同时必须区分「作者这么说」和「事实如此」——这个区分会延续到
  阶段二：参考答案只答作者的观点，不补充文章外常识。

理解写入 `data/eval_candidates/<文章名>.candidates.md` 开头（文件在此步创建，
以「## 通读理解」为节标题；data/ 已被 Git 忽略，含正文信息的产物不入库），
同时在回复里完整展示。写完**不暂停**，同一轮直接进入阶段一；
理解若有偏差，用户审候选时会指出，届时基于修正后的理解重出。

## 阶段一：只出问题候选列表

基于第 1 步的理解，产出 **3–5 道**候选，追加到
`data/eval_candidates/<文章名>.candidates.md`。同时在回复里展示。

每道候选包含：

```markdown
### 候选 1｜类型：原因或机制｜检索难度：普通
**问题**：作者为什么认为……？
**出题理由**：考查 <哪个信息需求>；证据集中在第 <a>–<b> 单元（<话题区名>）。
（话题块覆盖范围通常达 60–150 单元，单篇内的证据几乎总能落在 1–2 个话题块内；
此处说明的重点是证据所在话题区和是否连续，而非块数量。）
**自检**：两个人独立读文是否会标出相近要点/证据？范围提示是否泄露全部结论？
```

### 检索难度怎么判定

「难度」度量的是**检索系统把问题映射到正确 chunk 的难度**，
与拿到 chunk 之后能否组织答案（生成难度）无关。

| 等级 | 特征 | 典型场景 |
|------|------|---------|
| **普通** | 问题关键词在相关单元中直接出现，词汇高度重合 | 问"作者提到 X 的两个理由"，X 在证据单元里逐字出现 |
| **较难** | 问题用抽象概念，证据用同义词、具体例子或换了说法；或相关 chunk 附近有若干同主题干扰 chunk | 问"某机制"，证据用比喻或故事论证，没有直接点名机制 |
| **难** | 以下至少一种：① 问题与证据有明显词汇鸿沟（抽象 vs 叙事/比喻）；② 全文同类 chunk 多，正确 chunk 极易被淹没；③ 相关证据在读者预期之外的位置 | 问某抽象判断，全文用故事举例论证，没有任何直白句；或答案散落在多个离散位置 |

**自检方法**：把问题输入一个朴素关键词检索器，想象它会返回哪些 chunk——
若正确 chunk 大概率排在前三，难度是"普通"；
若正确 chunk 会被同话题其他 chunk 压下去，难度是"较难"或"难"。

候选间必须覆盖**不同的证据区域**（不同话题区或相距较远的位置），
不要多道题都盯着同一段。对照第 1 步的论据—位置地图检查覆盖情况：
理想情况是候选合起来覆盖了多数主要论据所在的话题区。类型从这些里选（详见指南）：
原因或机制 / 条件与限制 / 有边界的比较 / 有边界的综合 / 对明确论断的解释。

这一步**只出问题，不写答案**。理由：参考答案和证据标注是独立的人工审核对象，
混在一起会诱导"顺着问题编答案"。用户挑选后阶段二再展开，未选中的候选留在文件里备查。

出完列表后明确告诉用户：**从候选中挑几道（可以直接说编号），
我再为选中的题目写参考答案、答案要点和证据范围**。

### 出题时的负向清单

以下模式会毁掉评测价值，逐条对照：

- **主观感受/效果判断**：「这篇文章是不是信息量很大」——无金标准可言。
  改成问作者明确论证过的机制或取舍。
- **全文穷举**：「文章里多处提到 X，分别说什么」——证据过散。
  改成「在作者讨论的三个 X 观点中……」这类有边界的形式。
- **范围过大**：「总结全文观点」——Top-K 装不下。
  改成「作者给出某具体判断的两个核心理由是什么」。
- **问题里列完答案**：「作者是否认为 A 导致 B、C 导致 D」——题目自己答完了。
  范围提示（章节、数量限定）可以有，结论不能有。
- **预设未经证明的因果**：「因为……所以文章是不是……」。
- **互相重复**：多道题需要找回几乎相同段落时，删掉或换证据区域。

范围提示≠泄露答案：「在作者讨论的三个交易观点中」是限定范围（好）；
「文章里所有提到时间的地方」会诱导全文词语扫描（坏）。

要点数约束：普通题 1–2 个要点；有边界的综合题最多 3 个；
全文多点综合每篇最多留 1 道作为高难度观察样本。

## 阶段二：为选中题目写参考答案与证据

用户挑选后（例如"1 和 3"），回到导出的编号正文，为每道选中题目给出完整候选。
追加到同一文件 `<文章名>.candidates.md` 的「## 选中候选详情」一节，并在回复中展示。

每题包含四部分，格式对齐 eval curate 的数据模型（AnswerPoint/AnswerPoint 字段）：

```markdown
### 候选 1 详情
**问题**：<原文重复>
**参考答案**：<直接回答问题的简洁概括，2–5 句>
**答案要点**：
| claim_group | claim（独立可判断的单一结论） | 证据范围 | uncertainty |
|---|---|---|---|
| 适用条件 | <一句话结论> | [12–18] | <限定或"无"> |
**证据摘录**：每个范围给 1–2 句原文摘录（帮助人工快速核对，不必全文复制）
```

### 参考答案怎么写

- 直接回答问题，**不接受问题中未经证明的前提**，也不补充任何文章外常识；
- 覆盖所有重要要点，但不扩展到问题范围之外；
- 保留作者的限定词：「可能」「通常」「在某些情况下」——这些词进了不确定性
  字段就不该在答案里消失，反之亦然；
- 相关关系不得写成因果，建议不得写成保证，暂时缓解不得写成彻底解决。

### 答案要点怎么拆

一个要点 = 一个可独立判断真假的主要结论。一句话里两个需要不同证据的结论、
前半句对后半句可能错、同一要点跨相距很远的多个主题——都应拆分。
`claim_group` 是简短稳定的分组名（如「适用条件」「机会成本」「风险缓冲」），
不是完整句子。参考答案中每个重要结论都应有对应要点，要点中也不应出现
参考答案没回答、问题没问的额外主题。

### 证据范围怎么标

证据要**最小充分**：

- 最小：删掉过渡句、重复例子后仍能支撑要点；
- 充分：只看选中单元，读者能独立得出该结论；
- 直接：单元确实论证该结论，而不只是出现相同关键词；
- 一个要点由两个不连续位置支持时，写两个范围（如 `[12–18], [45–47]`），
  不要把中间大段无关内容圈进来。

简易测试：**只把这些证据交给另一个人，不依赖外部知识，他能写出这个要点吗？**
必须选中大量分散范围才能支撑的要点，优先缩小要点或建议改题。

`uncertainty` 记录影响结论强度或适用范围的信息：作者保留措辞、适用阶段/条件、
只有相关性没有因果、经验判断而非普遍规律。以下不算不确定性：「这是作者的观点」、
对要点的重复解释、用免责声明保一个没证据的强结论。没写"无"。

## 完成后

1. 提醒用户：这些是候选，请到 `uv run xifeng eval curate` 录入并人工逐项审核，
   参考 `docs/guides/evaluation-question-writing.md` 的检查表；
   审核时若有疑问，可对照文件开头的「## 通读理解」核查起草者当时的理解；
2. 如果某些候选在写作时发现题目本身有问题（证据过散、要点拆不出来），
   如实说明并建议改题或放弃，不要硬凑一个答案交差；
3. 报告证据分布情况：每个要点的证据范围是否集中在同一个话题区（理想）还是跨越
   多个话题区（排名风险增大）；每个要点 1–2 个紧凑范围为宜，不要把大段过渡句
   和无关内容圈进来。注意：话题块粒度很大（约 100 单元），单篇内几乎不存在
   容量问题，风险主要是同文章多个话题区语义相近导致正确块排名被压低。
